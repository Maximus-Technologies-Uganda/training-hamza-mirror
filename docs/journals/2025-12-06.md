## Retrospective: 5 Bullets

### 1. Key Decisions Made
- **Stateless JWT auth**: Chose client-side token storage over server sessions for GitHub Pages compatibility
- **Ownership on posts**: Added `ownerId` field to enforce write authorization
- **bcrypt for passwords**: Async hashing prevents blocking even with higher cost factors
- **Request ID propagation**: Client-provided IDs respected for distributed tracing support

### 2. Risks Identified
- **JWT secret management**: Default dev secret is insecure; production requires proper secret rotation
- **Token expiration UX**: 24h tokens mean users may face unexpected logouts; consider refresh tokens in future
- **No rate limiting on login**: Brute force protection should be added (account lockout or exponential backoff)
- **SQLite in production**: Current storage works but doesn't scale horizontally

### 3. What Changed from Original Plan
- **Simplified user management**: Used in-memory user store instead of full user registration flow
- **Deferred refresh tokens**: Original spec mentioned refresh tokens; deferred to future iteration
- **Health endpoint enhanced**: Added version and uptime to /health response (not in original spec)
- **Frontend auth context**: Implemented React context pattern for cleaner auth state management

### 4. What Went Well
- Contract-first approach caught API inconsistencies early
- Table-driven tests made auth edge cases comprehensive
- Request ID implementation was straightforward with Fastify hooks
- 303 tests passing with 80%+ coverage provides confidence

### 5. Next Steps
- [ ] Add password hashing strength configuration
- [ ] Implement account lockout after failed attempts
- [ ] Add refresh token rotation for better security
- [ ] Create user registration endpoint (currently seeded users only)
- [ ] Add audit logging for auth events
- [ ] Consider moving to PostgreSQL for production scalability
